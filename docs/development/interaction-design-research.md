# Piko 操作与跨设备交互研究

后续项目级方案见 [共用能力与自适应交互设计规范](adaptive-interaction-spec.md)。本文保留 2026-10-13 的研究依据与候选方案。

研究日期：2026-10-13。代码基线：`b4818cf6`。本文是设计研究与候选方案，不修改现行产品约定。

## 1. 结论与研究边界

这轮后台解耦已经提供了继续改进前端的基础：文件浏览位置有明确所有者，文件写入有执行身份和结果，导入草稿与查重有独立会话。当前主要问题是前端仍借助容器来定义工作：辅助上下文统一进入手机 Sheet，关闭上下文同时释放业务对象，任务入口用一个数字汇总多种性质不同的状态。

建议以“对象、操作、工作过程、呈现”四层组织前端。跨平台共享对象身份和操作含义；根据内容关系、可用空间和输入方式决定呈现。不要先规定每个功能只能使用某一种容器，也不要先实现一个覆盖全部业务的通用 Action 框架。

优先探索的组合是：

- 导入与查重报告拥有完整工作页面；短输入和当前内容的辅助控制继续使用弹层。
- 现有“任务”页作为恢复和执行结果的稳定入口，区分草稿、执行、报告与需要处理的结果。
- 需要快速切换时，再比较工作切换入口与紧凑恢复提示；桌面继续利用标签。
- 返回或关闭视图保留可恢复工作；放弃草稿、停止执行、移除报告各自明确。
- 操作能力、临时阻塞和入口优先级分别表达。

这些是基于代码和指南的设计判断，尚未通过用户试用验证。研究重点是文件、导入、查重、任务与它们的跨页面衔接；播放器、信息流、分享、账号与设置作为边界案例纳入，不声称已穷尽所有按钮和平台交互。

本轮完成静态代码追踪、原始指南阅读和历史截图检查。没有修改应用代码，没有新跑构建、UI 场景或真机测试。现有测试的覆盖范围通过源码确认，其历史通过记录不能代替本轮实测。

## 2. 证据及其适用范围

### 2.1 平台指南

本地资料来自相邻 `docmirror4a`，在文中链接原站以便跨设备使用。Material 3、Fluent 2 镜像抓取于 2026-09-21 UTC，Apple HIG、GNOME HIG 抓取于 2026-10-07 UTC。Windows、Android 自适应布局和 WAI-ARIA 页面于研究当日在线阅读；Android 外接显示指南抓取失败后通过浏览器补读成功。

| 资料 | 实际支持的判断 | 不应据此推导的结论 |
| --- | --- | --- |
| [Material Bottom sheets](https://m3.material.io/components/bottom-sheets/guidelines) | 标准 Sheet 服务于主体，可与主体同时交互，也能展开至全屏；模态 Sheet 阻止背景交互 | 所有辅助功能都应该放进 Sheet；必须固定露出三成背景 |
| [Material Tabs](https://m3.material.io/components/tabs/guidelines) | 用于同层级相关内容，不用来表达顺序步骤 | 手机禁止标签；任意工作实例都适合放入同一排分类标签 |
| [Material Badges](https://m3.material.io/components/badges/guidelines) | 小徽标表示未读通知，带文字的徽标可表达数量；标记依附于有含义的入口 | 一个红点能同时准确表达有草稿、正在运行、失败和未读 |
| [Apple Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets) | Sheet 与当前上下文紧密相关；复杂或长期流程考虑其他承载；创作内容可直接全高 | Sheet 只能有一页或只能是短表单 |
| [Apple Modality](https://developer.apple.com/design/human-interface-guidelines/modality) | 模态需要明确收益，内部层级应容易退出 | 独立编辑器必定要模态，或全屏一定意味着模态 |
| [Fluent Drawer](https://fluent2.microsoft.design/components/web/react/core/drawer/usage/) | 并列面板适合与主体同时查看和操作；覆盖面板更打断当前工作 | Drawer 是任意第二页面的通用位置 |
| [Android Canonical layouts](https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts) | 区分列表详情、信息流和辅助面板；布局变化时保持状态与内容关系 | 只看设备名称决定布局；将横向主辅比例套到所有纵向 Sheet |
| [Windows TabView](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/tab-view) | 管理可打开、关闭、切换的文档或页面实例，并提供相应键盘交互 | 文档标签与固定功能分类完全等价 |
| [Windows Command bar](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/command-bar) | 按重要性配置主要与次要命令，空间不足时移入更多菜单 | 菜单放不下就应该取消业务能力 |
| [Windows Touch](https://learn.microsoft.com/en-us/windows/apps/develop/input/touch-developer-guide) | 触摸与指针在精度、遮挡、触达和悬停方面不同 | 桌面一定有鼠标，移动端一定没有键盘 |
| [GNOME Selection mode](https://developer.gnome.org/hig/patterns/containers/selection-mode.html) | 批量管理可使用明确的选择模式、选择数量和操作栏 | 应把 GNOME 的每条选择手势直接复制到 Windows 文件管理器 |
| [Apple Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo) | 撤销应让人预测影响并看见结果 | 远端每项操作均可逆，或现有 Piko 已实现完整撤销栈 |
| [WAI-ARIA Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) | 标签要区分焦点与激活，并处理关闭后的焦点去向 | Web ARIA 属性可以直接替代 Compose 的平台无障碍实现 |

这些资料提供设计依据，不构成 Piko 的自动验收。不同平台对焦点和标签激活的建议也不完全相同，最终应遵守运行平台习惯并实测。

## 3. 用户究竟在操作什么

建议用以下词汇讨论需求，避免把所有东西称作“任务”或“上下文”。

| 对象 | 用户关心的内容 | 应保留到何时 |
| --- | --- | --- |
| 浏览位置 | 当前目录、搜索、筛选、滚动、选择 | 切走后可以恢复；主动导航时按明确规则调整 |
| 编辑草稿 | 来源、目标、选项、选择和预览 | 提交完成或明确放弃；是否跨重启另行决定 |
| 执行 | 本次提交的固定参数、进度、等待原因 | 得到可信结果；不能由页面是否存在决定 |
| 报告 | 一次扫描的范围、完整性、分组及后续处理 | 明确移除或失效；保留不代表永远有效 |
| 操作结果 | 哪些成功、失败、未执行、待确认，能否纠正 | 在可查询处保留到约定期限或用户移除 |
| 辅助视图 | 属性、排序、过滤、播放列表 | 关闭视图即可；其修改是否即时生效需明确 |
| 注意事项 | 需要输入、待核对、重要的新变化 | 查看与解决是两个不同状态 |

每个操作至少记录：作用对象、输入、适用条件、临时阻塞原因、产生的对象或结果、返回路径、取消边界、恢复方式。这里先定义讨论字段，不要求所有操作实现统一接口。

例如“移动到……”的对象是已固定的源文件，输入是目标目录，提交产物是一次移动执行；取消目录选择不移动文件，提交后离开页面不取消执行，失败或待确认从结果继续处理。标签、弹窗、手机全屏选择器都只是这个过程的不同呈现。

## 4. 核心操作地图

下表是本轮的功能级操作清单。它覆盖入口与流程类型，后续实现时仍需逐个核对平台能力、归档条目、上传中条目及混合选择等适用条件。

| 操作族 | 对象与输入 | 产物及恢复要求 | 推荐呈现 |
| --- | --- | --- | --- |
| 打开目录、上级、后退、定位 | 位置或文件 ID | 浏览位置；区分历史后退与层级上级 | 页面或文件标签，定位后高亮 |
| 搜索、排序、类型筛选 | 范围、关键词和条件 | 列表投影；保留可见条件及清除入口 | 就地搜索，短菜单或 Sheet |
| 列表、网格、画廊切换 | 当前集合与显示偏好 | 同一内容的视图；避免不必要地清空工作 | 当前页视图控制 |
| 多选、全选、范围选择 | 明确范围的可见条目 | 选择集；不等于执行 | 选择模式与操作栏 |
| 新建目录、单项改名 | 目标目录或文件、新名称 | 写入执行及结果 | 就地输入或短对话框 |
| 批量改名、规范命名 | 文件集合、命名规则、预览 | 可核对的修改计划和批次结果 | 完整编辑区；是否暂存按成本决定 |
| 星标、固定快速访问 | 文件或目录、开关值 | 修改结果或偏好 | 可见切换项，按需反馈 |
| 移动、复制到 | 固定源集合、目标目录 | 执行及逐项结果 | 专用目标选择过程 |
| 剪切、复制、粘贴 | 源集合及来源、当前目标 | 剪贴板意图；粘贴后产生执行 | 桌面快捷键与菜单，触屏可见替代 |
| 移入回收站、恢复 | 文件集合 | 执行；可用时提供撤销 | 选择操作栏、上下文菜单 |
| 彻底删除、清空 | 对象与明确范围 | 不可逆执行及结果 | 描述范围的确认；不与关闭视图共用文案 |
| 添加链接、分享转存、秒传 | 来源、目标、选项与文件选择 | 草稿、一次或多次执行、结果 | 简短初始输入，复杂时完整编辑页面 |
| 上传 | 本地来源及云端目标 | 准备与上传执行 | 系统选择器、目标核对、任务详情 |
| 下载、选择画质 | 云端文件、画质及本地目标 | 本地下载执行 | 直接动作或短选项；结果去任务页 |
| 片段下载 | 媒体、时间范围、画质 | 预览决策及下载执行 | 足够空间的专用编辑面板或页面 |
| 打开压缩包、解压 | 条目、密码、目标 | 虚拟浏览或解压执行 | 浏览页；密码是可恢复的待输入状态 |
| 归档、取消归档、恢复归档内容 | 文件夹或归档条目、选项 | 清单修改、远端执行及结果 | 核对过程，执行留在任务页 |
| 查重 | 固定根目录 | 扫描及带完整性说明的报告 | 报告页面；桌面可开标签 |
| 分享、管理分享 | 文件集合、有效期等 | 分享链接及管理记录 | 简短配置，后续从“我的分享”管理 |
| 查看属性、复制来源 | 文件或记录 | 辅助信息或剪贴板结果 | 侧面板、Sheet 或详情 |
| 播放、信息流、定位来源 | 媒体与播放范围 | 播放会话、浏览位置 | 专用媒体视图；返回保留来源工作 |
| 暂停、停止、重新查询、重试 | 具体执行及状态 | 状态转换或新执行 | 任务行常用动作与详情 |
| 撤销、移除记录 | 指定结果 | 逆向执行或仅移除记录 | 明确操作名与影响范围 |
| 切换账号、修改设置 | 账号或配置 | 工作区切换或配置变更 | 稳定导航；不混进工作实例切换 |

一个动作不必永远对应同一种控件。“添加链接”开始时只有一个输入框，解析后可能是几百个文件，提交后又变为后台执行。可以逐步增加内容空间，但不应要求用户先理解通用的“半开、展开、详情”容器层级。

## 5. 能力规则与入口安排

建议先拆清三类决定：

1. **适用性**：对象是否支持操作。例如压缩包虚拟条目与真实网盘文件不同。
2. **当前可用性**：此刻是否被执行冲突、账号状态或其他条件阻塞，以及原因。
3. **呈现优先级**：当前页面是否常用、放直接按钮还是更多菜单、标签和快捷键是什么。

菜单空间不足只影响第三类。当前归档规则包含“手机菜单已经满”的解释，应回到业务逐项判断是否支持跨目录归档；不能仅删除限制就宣称所有库页面都已支持。

不适用的操作可以不显示。用户预期存在、但暂时不可执行的操作宜保留并说明原因。仅依赖灰色和悬停提示对触屏不足；可以在相关位置显示原因，或允许打开解释。最终提交仍由业务层重新检查，处理用户打开菜单后状态变化的情况。

混合选择必须逐操作规定：全部对象都支持才启用，还是只处理支持的子集。后者应在提交前说明“对 N 项中的 M 项执行”，不能静默跳过。异步列举目录时还应区分“选中 N 个文件夹”和最终文件数。

实现上可先沿用 `DriveActions` 的名称和图标、`FileCommands` 的执行检查，整理重复的 UI 判定。只有实际出现重复协议时，才提取轻量操作描述；不要把播放、导航、远端事务和设置保存强行塞进同一执行器。

## 6. 生命周期与退出规则

以下是建议规则，需要与现行关闭行为区分。

| 用户动作 | 视图 | 草稿、扫描或结果 |
| --- | --- | --- |
| 返回到来源页面 | 离开当前工作视图 | 保留可恢复工作，不暗中提交或停止 |
| 切换工作 | 激活另一个视图 | 保留当前输入、选择及合理的滚动位置 |
| 收起辅助面板 | 隐藏或缩小面板 | 按业务规则继续；与放弃分离 |
| 放弃草稿 | 关闭编辑器 | 丢弃未提交输入；已有远端提交需独立结算 |
| 停止扫描 | 可以留在报告 | 停止继续发现，明确显示部分结果 |
| 移除报告 | 关闭或切换报告视图 | 丢弃报告，不恢复此前删除的文件 |
| 取消执行 | 不决定视图去向 | 只在业务支持时提供，说明已完成部分 |
| 撤销已确认修改 | 显示处理状态 | 产生逆向操作，可能失败或部分成功 |
| 移除结果记录 | 列表移除记录 | 不撤销远端修改，不伪装成取消 |
| 切换账号、结束进程 | 工作区退出 | 各业务有不同能力，必须另列恢复边界 |

桌面标签的 × 可以关闭视图并保留工作，也可以结束一次临时工作，但两种方案不能混用而不说明。推荐对已投入输入的草稿和仍运行的工作采用保留视图外对象的方案；对空草稿可直接回收。为避免保留对象无限积累，需要稳定的工作列表、明确的放弃动作和清理规则。

自动暂存必须有准确承诺：当前会话内保留不等于已落盘。现有文件位置恢复、上传续传与内存草稿属于不同能力，不应统一文案为“下次继续”。若未来承诺跨重启草稿恢复，需要另行设计账号隔离、保存格式、敏感来源处理和恢复失败提示。

“返回”也不能由一串组件的声明顺序长期决定产品语义。建议逐流程明确：输入法先由系统处理；当前局部浮层或选择过程先退出；然后退出选择/搜索等局部模式；最后离开工作页面。目录选择中的“上一级”和“取消选择”要有不同入口。具体 Android 返回优先级仍须真机验证，尤其是 IME、预测性返回和嵌套报告导航。

## 7. 承载方式：比较候选而非先定组件

| 方案 | 收益 | 主要代价 | 适用条件 |
| --- | --- | --- | --- |
| A. 现有多工作 Sheet + Pager | 已实现，工作常可见，切换快捷 | 背景长期占位；手势与层级多；复杂内容空间不足 | 同一主体的少量互补内容，而非任意独立工作 |
| B. 完整工作页面 + 现有任务入口 | 编辑空间充分，恢复位置稳定，新增导航最少 | 切换通常先到列表；“任务”要能解释草稿与报告 | 恢复频率中低、工作数量不大，适合作为基线 |
| C. 完整工作页面 + 专用工作切换入口 | 可从当前页面直接选其他工作，不必访问执行列表 | 新增常驻入口，可能与“任务”重复；右上角触达成本 | 高频交替编辑，列表能显著改善切换 |
| D. 完整工作页面 + 最近工作摘要 | 最近一项容易恢复，低学习成本 | 占用内容或底部区域；多项仍要列表；与播放器竞争 | 少数明确需要快速往返的长流程 |
| E. 所有工作都变成主导航项 | 直接访问 | 把功能类别与实例混合，数量不稳定 | 不建议作为通用方案 |

当前优先选择 B 作为原型基线，再与 C 做比较。理由是现有任务页已经持有恢复入口，先改善对象与分组即可形成完整流程。若真实使用表明“文件—草稿—报告”切换频繁，再增加 C；不因右上角空间看起来空闲就加入新入口。

工作切换与执行管理可以共享数据来源，但不必呈现相同列表。前者重点是“我正在看哪些东西”；后者重点是“哪些工作在执行、出了什么结果”。同一草稿关联的提交可折叠显示，不能一项工作在两个列表里各自拥有不同关闭含义。

### 7.1 右上角入口与小红点

右上角展开恢复列表是有效候选，关键价值来自稳定入口与可辨识列表，小红点本身不能承担导航含义。

需要分别讨论三件事：入口放在哪里、展开呈现什么、标记表达什么。可以先用有名称和无障碍标签的图标，展开列出来源、目标、状态与最近编辑时间；选择一项恢复完整工作页面。手机可用 Sheet 展示这个短列表，桌面可用锚定弹层。此时 Sheet 承载的是工作选择，不承载每个工作的全部编辑器。

| 状态 | 推荐表达 | 清除规则 |
| --- | --- | --- |
| 有可恢复草稿 | 列表内明确分组；如需数字则注明是在数草稿或工作 | 直到提交或放弃；打开列表不应让对象消失 |
| 执行中 | 任务入口或列表内进度；不必持续红点 | 随执行结束变化 |
| 有新结果尚未看过 | 未读标记，可用小徽标 | 查看对应结果后清除未读；结果仍保留 |
| 需要用户输入或核对 | 列表内“待输入密码”“结果待确认”等明确状态 | 解决问题后清除待处理；仅打开列表不算解决 |
| 历史成功报告 | 普通可恢复条目 | 按明确的移除或保留规则处理 |

颜色不单独承担含义。Material 默认徽标使用强调性的颜色，小红点也并非天然错误；问题在于把“有东西”和“需要注意”混成一个永久标记。未读与待处理可同时存在，应在对象状态中分开记录。

入口最好在无工作时仍可预测，或至少让用户知道恢复位置；空状态可解释用途。位置不能仅因为有无工作反复挤动搜索等常用按钮。右上角也可能被账号、搜索、窗口按钮占用，需要分别检查手机单手触达、桌面窄窗和全屏工作页，而不是所有界面统一贴一个点。

## 8. 空间、输入方式与平台习惯

当前按平台分交互模型有具体历史原因：平板因宽度进入桌面布局后，依赖右键的操作不可达。因此不建议简单删掉 `FormFactor`，也不建议把 Android 永久限定成放大的手机。

布局至少考虑：窗口宽与高、输入法后剩余空间、字体缩放、内容最小可用尺寸、触摸与指针支持，以及平台导航习惯。输入可以同时存在；不要随着最后一次鼠标或触摸事件整体重排界面。

| 环境 | 内容安排 | 必须保留的操作能力 |
| --- | --- | --- |
| 手机竖屏 | 一次一个主要工作页面；短辅助内容用弹层 | 可见更多入口、明确选择模式、系统返回 |
| 手机横屏或输入法展开 | 优先保证正在编辑的内容和确认操作；避免强制半高布局 | 不依赖拖拽展开才能看到主要按钮 |
| 平板触屏 | 有价值时并列工作列表与编辑器、报告分组与详情 | 大触控目标、无需悬停的操作入口 |
| 窄桌面窗口 | 收拢命令和辅助面板，保留标签切换或列表替代 | 快捷键、焦点路径、上下文菜单 |
| 宽桌面窗口 | 标签与有关系的并列面板 | 可见常用命令；右键和快捷键用于提效 |
| 混合输入、外接显示 | 按当前窗口适配内容，不因设备名称关闭能力 | 触控、键盘、指针均可完成主流程 |

Android 官方外接显示指南也要求按运行时窗口和能力适配，并在配置变化后保持工作状态；手机连接外屏后仍是同一设备型号，设备标签不足以决定布局。[依据](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-connected-displays)

不要只为填满宽屏加第二栏。文件属性与当前文件是主辅关系，报告分组与组内文件是列表详情关系，两个任意草稿则是独立工作。它们需要不同的导航和焦点规则。

选择也须区分焦点、选中对象和激活。键盘焦点移动不应自动打开文件；触屏进入多选后点条目切换选中，退出模式有明确入口。文本框内 Ctrl+A、Ctrl+Z 优先作用于文本，不能被文件页全选或账号级撤销截获。标签关闭后焦点回到合理相邻项，弹层关闭后回到发起控件；这些需要平台语义树和真实输入验证。

## 9. 六条完整流程的设计检验

### 9.1 添加链接，暂离后继续

进入草稿 → 输入与解析 → 核对来源、选文件和目标 → 提交 → 查询结果。

选择目标是草稿内部过程，确认后返回原草稿。需要自由浏览时则保留草稿并离开，通过任务或工作列表恢复。新草稿默认目标继续采用打开时快照，普通文件导航不修改它。主动另选、目标被删除、账号变化分别处理。

验收重点：输入、选择、目标和展开状态不串到另一草稿；返回不提交；外部链接在已有编辑过程中到达时不覆盖旧输入；解析中的取消与远端提交后的离开不同；结果不因编辑器移除而丢失。

### 9.2 查重、继续浏览、处理报告

确定扫描根目录 → 开始扫描 → 可离开浏览 → 恢复报告 → 比较和选择 → 执行处理 → 查看结果。

报告显示扫描范围与完整性。停止扫描得到部分结果，不能显示成完整扫描无重复。报告保留后可能过时，实际删除、移动等仍应检查对象当前状态。移除报告不会撤销已经执行的修改。

手机一次只允许一个查重目前是实现规则，不是平台限制。研究阶段保留它作为约束，但若引入稳定工作列表，可重新评估“多份报告、一份扫描”或多扫描的成本。不能仅因为桌面支持多个就直接对手机放开后台资源消耗。

### 9.3 多选后移动到其他目录

固定源集合 → 打开目标选择 → 浏览候选位置 → 确认 → 提交执行 → 查看成功、失败及待确认部分。

取消目标选择应返回原选择。确认时重新校验账号、目标、冲突和自包含关系。执行被接受后可以退出选择模式；后续失败从执行结果处理，不应依赖旧页面选择集自动复活。移动与复制到原目录的规则不同，入口不能只共享一个没有业务校验的选择器。

搜索结果、画廊和库里的源文件可能来自多个父目录，应保留真实来源；不能用当前页面地址作为所有源文件的父目录。

### 9.4 远端请求结果不确定

提交 → 网络中断或响应丢失 → 显示结果待确认 → 重新查询 → 根据已确认结果继续。

“重试”可能重复执行，“重新查询”只核对状态。已确认、失败、未执行、待确认集合应保持可见。批次部分成功时，可以撤销已确认部分或处理失败部分；哪些动作实际支持，以业务会话能力为准。

这类结果适合进入“需要处理”的集合。用户看过后可清除未读，但不应因看过而被当作已解决。

### 9.5 播放或信息流中定位文件

保留媒体上下文 → 在文件位置定位 → 查看或操作 → 明确返回媒体上下文。

定位页面与主浏览位置的关系必须保持一致：临时查看不应意外覆写其他工作位置。是否继续音视频、暂停自动发现、保留播放位置属于媒体流程自身，不由通用“隐藏页面”规则一刀切。此流程需要补查真实播放器与信息流后再定，当前不据静态文件浏览代码推断完整体验。

### 9.6 换号、窗口变化与重启

窗口变化只改变呈现，不应重复提交或丢掉当前工作身份。换号后旧账号结果不能混入新账号入口；旧行的迟到操作不能关闭新会话。重启后只恢复确实持久化并能安全重建的对象。

导航 key 可序列化不代表它引用的草稿、扫描会话或远端执行一定可恢复。恢复失败要回到可理解的位置，说明哪些工作无法继续，不能留下指向不存在对象的空页面。

## 10. 前端结构的渐进调整

不建议第一步重写全部导航或业务会话。可以按下面顺序推进，每一步都能独立评估：

1. **统一术语和结果入口**：列清返回、放弃、停止、移除、撤销的含义，修正入口间不一致的表述；定义草稿数、执行数、待处理数各自范围。
2. **形成可查询的工作摘要**：沿用现有草稿和执行身份，投影标题、来源、目标、阶段、恢复动作与可用操作。摘要不再拥有业务生命周期。
3. **分开视图关闭与对象释放**：工作列表可以恢复尚存对象；空草稿可以回收；显式放弃走原来的业务释放链。先解决所有权，再替换容器。
4. **让手机导入与报告直接获得合适空间**：以完整页面方案为基线，取消必须经“查看更多”才能进入完整工作区的固定流程。短表单是否使用全高 Sheet 作为另一种外壳，可以单独比较。
5. **整理能力与呈现规则**：先处理已确认混杂的归档入口、批量操作和临时阻塞；保持提交端校验。
6. **比较恢复入口**：现有任务入口与专用工作切换入口使用同一组真实场景，不同时引入多个新入口。
7. **再扩展平板与混合输入布局**：选择真正有并列价值的内容关系，验证触屏入口、键盘焦点及宽高变化。

可能需要的概念边界是“工作身份”和“视图身份”，不意味着立即为每个对象新增一套 ID。先保持一份工作一个视图；只有允许同一报告多处打开时，才需要独立视图实例。不要提前建立多窗口框架。

`WorkspaceViewModel` 可以继续协调账号级呈现，但 Sheet 展开档位应属于承载它的 UI，业务对象是否存在由所有者负责。现有 `TaskContinuations` 的身份复核值得保留；新摘要应复用其逻辑，避免旧任务行操作误作用于替换后的对象。

## 11. 验证方案与决策标准

### 11.1 现有覆盖和缺口

`WorkspaceContextsSmokeTest` 包含独立身份、关闭、已发布标签恢复、缓存读取期间打开草稿及迟到操作等场景。`shots/.../WorkspaceContextScenario.kt` 使用真实 `PikoApp` 与假服务端，覆盖手机 Sheet 切换、草稿输入保留、详情往返、查重复用/替换和桌面多上下文。它证明的目标是当前设计下状态是否保持，不证明用户容易理解这套设计。

更换容器后保留业务不变量的测试，调整与旧容器形态绑定的断言。不要为了新 UI 名称重写一遍同构测试，也不要把“有 70% 的 Sheet”当作未来不可改变的需求。

### 11.2 原型对比任务

使用同一份数据和相同业务规则比较 B 与 C。先测真实工作恢复，再测装饰和动画。

| 任务 | 观察内容 | 失败信号 |
| --- | --- | --- |
| 两份来源相似的导入草稿间切换 | 能否凭标题、来源和目标辨认 | 打开错误草稿、覆盖输入 |
| 编辑中去目录核对，再返回 | 恢复入口是否被发现，状态是否完整 | 以为草稿丢失或重新创建 |
| 扫描中离开，再查看部分报告 | 能否区分离开、停止和移除 | 误结束扫描、误认为部分报告完整 |
| 从搜索结果移动多项 | 源集合和目标是否清楚 | 错误范围、错误目录或重复提交 |
| 请求响应丢失后处理 | 能否发现并理解待确认 | 直接重做已有成功部分 |
| 看到角标并打开工作列表 | 能否解释数字、未读与待处理 | 为消除红点误删除或误认为问题已解决 |

记录首次成功率、恢复耗时、误操作、返回层数、切换次数和用户对状态的解释。步骤更少只是一个指标：专用入口若少一步却更难发现，不算胜出。没有真实数据前，不填主观分数伪装成量化结论。

### 11.3 平台与边界矩阵

- 手机竖屏、横屏、输入法展开；长文件名、大字体及屏幕阅读器。
- 平板触屏、平板接键鼠、窄桌面、宽桌面触屏；主流程均不用右键也能完成。
- 空草稿、单份工作、多份同名工作、无报告、部分报告、失败、待输入、待确认。
- 弹层打开后目标删除、权限或账号改变；列表变化后旧行被点击。
- 切换、返回、显式放弃、换号、窗口重建、进程退出分别验证。
- 文本编辑时快捷键不触发文件操作；弹层关闭、标签关闭、布局变化后焦点合理。
- 报告中的多选、滚动、文件操作与 Sheet 手势互不抢占；主按钮不被 IME 遮挡。

在实际实现阶段，通过假服务端检查请求数量、源 ID、目标 ID、账号和结果记录，验证既没有丢请求，也没有重复提交。原生 Android 手势、输入法和后台限制仍需真机；桌面原生输入和窗口行为需对应平台验证。

## 12. 下一轮需要作出的少数决定

最先值得确定的是：返回工作页是否默认保留草稿和报告、保留到哪个生命周期、任务页如何清楚地找到它们。它们决定后端所有权和前端导航的接缝。

随后用原型决定是否需要专用工作切换入口，以及它应放在顶栏、任务入口附近还是其他位置。右上角图标是候选，小红点只是标记策略的一种，不作为预设答案。

暂不需要决定全应用每个动作的最终组件，也不需要一次性实现持久化、多窗口和通用命令框架。先完成上述几条完整流程，才能用具体失败或使用收益决定下一步拆分。
