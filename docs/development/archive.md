# 文件夹归档

归档先写清单并确认成功，再处置对应原文件。八个目录可同时处理，CID 取样最多并行 16 个，
同一 GCID 和大小只取样一次；可选 CID 取样超时后仍保存归档记录。所有账号默认将原文件移入回收站，可取消该选项以永久删除。
永久删除前保留可恢复依据。撤销时跳过仍在原位的相同文件。

确认框可选择“只归档大文件（至少 50 MiB）”。清点数量、大小、无来源文件与实际操作使用同一门槛，
低于门槛的文件不取详情、不取样 CID，也不处置。此选项与“包含无来源记录的文件”分别生效。

保存文件时所有账号均创建真实网盘文件，检查所需空间与上传消耗，不自动保存为归档引用。
打开归档条目时所有账号均按剩余容量限制临时取回的总大小。

文件夹菜单的“取消归档”递归恢复该目录及子目录中的归档条目，未归档的文件保持原样。
恢复优先使用回收站中同目录、同名、同 GCID 和大小的原文件；原文件已不在时才秒传，并检查所需空间。
恢复失败的条目继续保留，成功恢复支持撤销。

## 来源与取回元数据

有来源的归档会在同目录保存 `归档来源-<标识>.magnet` 或 `.txt`，内容是完整磁力或分享链接。
同一来源只保存一份；这些文件在官方客户端中可见，不参与后续归档。可复制链接到其他下载器或浏览器恢复内容，
不依赖 Piko；来源失效或无人提供种子内容时仍可能无法恢复。

取回后清单保留文件名、大小、GCID、CID、来源及 `restoredFileId`，但不再显示为归档条目。
Piko 按真实文件 ID 与内容标识补回来源；改名后仍可识别，再次归档时保留来源与已有 CID。
旧清单缺少 `restoredFileId` 时仍按归档条目读取。新清单中的已取回记录需要新版 Piko 识别。
来源文件和清单写入成功后才处置原文件；来源文件同名但内容不匹配时停止归档。

## 并发实测

开发 CLI 可复现只读实验：

```powershell
.\gradlew.bat :cli:installDist
.\cli\build\install\piko-cli\bin\piko-cli.bat archive-bench /Dramas --parallel 4,8,16,32,64 --count 128 --timeout 15
```

实验仅接受 Dramas 内的路径，仅读取详情及 CID 的三个窗口，不写清单、不归档文件。
独立实验客户端解除 SDK 每秒 5 次请求和 HTTP 每主机队列的限制，并记录实际网络在途峰值、
HTTP 尝试数和 429 响应；输出不含账号凭据或下载直链。出现任务失败后停止该阶段升档。

2026-10-01，Dramas 内 128 个文件，单轮结果：

| 任务并发 | 详情吞吐（文件/秒） | CID 吞吐（文件/秒） | CID 网络在途峰值 |
| --- | ---: | ---: | ---: |
| 4 | 19.76 | 7.55 | 4 |
| 8 | 40.48 | 16.36 | 8 |
| 16 | 54.19 | 30.76 | 16 |
| 32 | 140.81 | 50.61 | 32 |
| 64 | 258.06 | 77.72 | 63 |

每档详情 128 次、CID 384 次 HTTP 尝试全部成功，无重试或 429。详情真实网络峰值达到 64。
这是此账号、网络、内容与测试时刻的可接受并发下界，尚未测到服务端硬上限；CDN 缓存热度会影响耗时。
首轮使用默认 HTTP 调度器时详情吞吐在约 25 次/秒处停止增长，不能据此判断服务端限流。

每账号每秒 16 次 API 请求、16 个 CID 任务、5 秒取样超时的完整只读链路，128 个文件的一轮全部成功，
约 8.18 秒完成。此前两轮各有一个取详情超时，无 429；CID 可选，超时会省略 CID，不阻止清单记录。

## 清单写入实测

```powershell
.\cli\build\install\piko-cli\bin\piko-cli.bat archive-write-bench /Dramas --parallel 2,4,8,16,32 --count 32 --timeout 60
```

写入实验在 Dramas 内新建独立测试目录和子目录，使用真实 `VaultStore` 上传清单、等待一秒、确认版本，
每个目录每轮加入 16 个不同的测试记录。不处置已有文件；最后核对测试目录的父目录与名称，
只删除本次创建的目录，并等待列表确认清理。若进程退出导致清理未完成，可凭日志中的完整名称和 ID 使用
`archive-write-cleanup /Dramas --probe-id <ID> --probe-name <完整名称>`，身份不匹配时拒绝删除。

使用不同内容的清单时，2/4/8/16/32 并发全部成功，32 并发约 3.27 秒完成，无 HTTP 429。
旧实现每档实际上传了 42～49 份清单：刚上传的版本尚未出现在列表中，或后续列表暂时回退，
导致被误判为写入冲突而删除重传。确认现在以短间隔等待自己上传的版本可见，看到更高版本时仍立即认输，
保留同版本随机串排序规则及延迟确认。

使用应用每秒 16 次 API 的预算，32 个目录的实测：

| 目录并发 | 总耗时 | 单目录 P95 | 成功目录 |
| --- | ---: | ---: | ---: |
| 2 | 40.55 秒 | 4.96 秒 | 32/32 |
| 8 | 14.80 秒 | 6.01 秒 | 32/32 |
| 16 | 13.25 秒 | 7.40 秒 | 32/32 |

各档无 429，测试目录已确认清理。应用采用 8 个目录并发，相比 2 个约快 2.7 倍；
16 个的额外吞吐收益较小，单目录等待更长。上述数据来自首次可见性等待修复，最终修复也覆盖延迟确认列表回退。

最终实现以 8 并发、每秒 16 次 API 再测 32 个目录：全部成功，耗时 11.37 秒，单目录 P95 2.84 秒。
实际只上传 32 份清单，无重复上传或 429；测试目录已确认清理。
