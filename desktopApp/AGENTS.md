# desktopApp 模块

Windows、macOS 与 Linux 的应用入口、原生系统能力实现及独立播放器/信息流窗口。应用内更新的版本检查与跨平台安装细则见 `../shared/src/commonMain/kotlin/dev/piko/shared/update/AGENTS.md`，桌面端凭据机密存储见 `../shared/src/desktopMain/kotlin/dev/piko/shared/auth/AGENTS.md`。

## Windows 与通用桌面运行时

### 界面库与播放器版本锁定

- **版本组合**：桌面运行时固定停留在 Compose Multiplatform `1.12.0`、Material 3 `1.12.0-alpha03` 与 MediaMP `0.5.0`（与 Animeko 保持一致）。CMP `1.13` alpha 附带的 Skiko `0.152` 将底层渲染后端封装进 `OnScreenRedrawer`，而 MediaMP `0.5.0` 的 D3D11 零拷贝表面必须直接读取 `Direct3DRedrawer`，升级后打开播放器即崩溃。
- **插件与运行库分离**：Gradle 打包插件单独采用 CMP `1.13` alpha 以使用该版本起提供的 Release AOT 缓存 DSL；因此 `desktopApp/build.gradle.kts` 不使用 `compose.desktop.currentOs`，而是显式按 `1.12.0` 版本号声明各平台运行库坐标。Material 3 `1.12` 中部分 API 为实验性（`ui` 模块已统一 opt-in），且缺少不可点击的 `SegmentedListItem`，设置页以 `StaticSegmentedRow` 替代。
- **构建类路径净化**：Compose 与 MediaMP 桌面依赖会传递引入 `ui-test`、`junit`、`truth` 与 `kotlinx-coroutines-test`，已在 `desktopRuntimeClasspath` 中显式排除，不影响测试类路径。
- **播放后端排空与定位（`MediampPlaybackBackend`）**：切换播放源或关闭播放器前必须通过 `stopAndAwaitIdle()` 轮询等待 mpv 进入 `idle-active=yes` 以排空异步输入线程，随后再关闭本机回环代理流；外挂字幕因 MediaMP `0.5.0` 忽略 `MediaExtraFiles`，经反射获取内部 `MPVHandle`（`getHandle$mediamp_mpv`）调用 `sub-add` 挂载；信息流预览（`keyframeStart = true`）或流总长未知时，绕过 MediaMP 硬编码的 `absolute+exact` 与 `0` 截断，直接经底层 `MPVHandle` 下发 `seek`（`absolute+keyframes` / `absolute`），防止撑爆 `8 MiB` 预览解复用队列；字幕回退字体根据 `PikoLocale.effectiveLanguage` 动态匹配简繁系统字体（Windows 微软雅黑 / 微软正黑体，macOS 苹方 SC / TC，Linux 已安装的 CJK 字体）。

### Release 打包、ProGuard 与 JDK 25 AOT 缓存

执行 `./gradlew :desktopApp:packageReleaseMsi`（或 `createReleaseDistributable`）构建发布包，jlink、jpackage 与 ProGuard 统一绑定 **Azul Zulu JDK 25** 工具链（与运行 Gradle 的 JDK 解耦；Temurin 25 不附带 `jmods` 目录会导致 ProGuard 与 jlink 失败，且不发布 Windows ARM64 JDK 25）：

- **ProGuard 裁剪（仅裁剪不混淆）**：规则位于 `desktopApp/proguard-rules.pro`。除 JNA、MediaMP 与 `ServiceLoader` 实现外，凡通过 `MethodHandles` 按方法名查找并交由 FFM 执行 upcall 回调的方法（如 `WindowsCaption` 窗口过程、FFmpeg 转封装的 `AvioReader.read` 与 `seek`），以及 `compose-windows-touch` 反射调用的 Compose 内部多指针方法，在字节码中均无直接调用点，**必须显式编写 `-keep` 规则**，否则仅在 Release 包中静默失效且 Debug 无法发现。CI 打包后统一运行 `java -Xverify:all desktopApp/package/VerifyClasses.java` 对产物 jar 执行全量字节码校验。
- **AOT 训练隔离与 CPU 指令集兼容**：打包期间会真实拉起一次带 `-Dcompose.aot.training-run=true` 的训练进程（弹窗运行 `12 秒` 后由 `Main.kt` 自动退出以写出 `app.aot`，且不参与单实例锁）。`build.gradle.kts` 在训练前临时向启动配置注入独立的 `build/aot-training-home` 数据目录并在训练后移除，防止正式包因未带 `piko.home` 而在训练期间读写打包机上真实的 `~/.piko`（曾导致本机打冒烟包时将当前账号登出）。训练与正式运行均必须携带 `-XX:-AOTAdapterCaching -XX:-AOTStubCaching`：JDK 25 默认将训练机生成的调用适配机器码写入缓存且加载时不校验宿主 CPU 特性，CI runner 具备 AVX-512，装入不支持 AVX-512 的用户 CPU 会在 `AdapterBlob` 处随机崩溃。
- **类路径时间戳与时区校验闭环**：JDK 25 AOT 缓存严格按类路径上每个 jar 的字节大小与秒级修改时间校验（`aotClassLocation.cpp` 仅对 `lib/modules` 豁免时间检查，无放宽选项），任意一个 jar 失配即整份缓存作废：
  1. **MSI 偶数秒与本地时间偏移**：MSI 内部的 CAB 仅精确到偶数秒且存储无时区的本地时间，安装时按用户机器时区解释（例如 CI 在 UTC 打包、用户在东八区安装，所有 jar 修改时间会偏移 8 小时）。因此训练前先将全部类路径 jar 统一对齐至同一个偶数秒时间戳并以 `-Dpiko.classpath-mtime` 写入启动配置；用户首次启动新装 MSI 时由 `ClasspathTimes.kt` 按该属性将 jar 修改时间修正回训练值，自**第二次启动**起正式命中 AOT 缓存。CI 安装冒烟在东八区环境安装 MSI，校验首次启动修正后的 jar 时间，并在第二次启动时通过 `-Xlog:class+path` 验证通过类路径校验（注意：`Opened AOT cache` 日志在校验之前即输出，不能作为命中依据）。
  2. **便携包采用 `.7z` 格式**：`.zip` 标准头仅存打包机本地时间，且 Windows 资源管理器与 `Expand-Archive` 均忽略 zip 的 UTC 扩展时间戳，跨时区解压会导致 AOT 缓存整份作废；`.7z` 原生存储 UTC 时间（`.github/scripts/pack-portable.ps1`），解压即直接命中 AOT 缓存。
- **MSI 事务升级与残留清理**：生成 MSI 后由 `package/windows/transactional-upgrade.ps1` 将卸载旧版移入安装事务（新版安装失败时保留旧版文件，但 Windows Installer 会将其记为「已通告」状态，后续应用内更新自动降级为打开下载页），并向 `app` 目录注入 `*.jar`、`*.xml` 的 `RemoveFile` 规则，确保应用内补丁更新引入的新文件名 jar 在卸载时一并清除。

### 原生库、FFmpeg FFM 转封装与 GPU 设备失效恢复

- **随包原生库与延迟图片加载器**：mpv 与 FFmpeg DLL 预解压置于应用资源目录 `mpv/` 下，启动时在后台调用 `MpvMediampPlayer.prepareLibraries` 指向该目录（避免 MediaMP 默认每次启动向 `%TEMP%` 重复解压且无法清理），创建播放器窗口前由 `BundledMpvRuntime.ensure()` 最多等待 `3 秒`。JNA 的 `jnidispatch.dll` 在构建时从实际依赖的 `jna` jar 提取至 `jna/`，`main` 首行通过 `useBundledJnaDispatch()`（`BundledNatives.kt`）指定路径并禁止自动解压（不写入 `jvmArgs`，因为 `:desktopApp:run` 不会展开 `$APPDIR`）。Windows 系统通知经 FFM 直调 `combase` 与 COM 虚表（`WindowsToast`），不依赖 `kotlin-winrt`；仅 MSI 安装版在首次启动后台线程中向 `HKCU\Software\Classes\AppUserModelId` 注册通知 AUMID 与图标（避免开发版或便携版覆盖正式版图标）。`installImageLoader()`（`DesktopImageLoader.kt`）必须在 `PikoProxySelector.install` 之后执行，将 Coil 磁盘缓存定向至 `PikoHome.root/cache/images`（避免私人缩略图落入系统 `%TEMP%/coil3_disk_cache`）并将 OkHttp 单主机并发上限调高至 `32`（总并发 `96`）。
- **FFmpeg 8 FFM 直调转封装（`media/Ffmpeg.kt`、`FfmpegRemuxer.kt`）**：片段截取与转码档 TS 转封装通过 FFM 直接加载 `mpv/` 目录内随带的 FFmpeg 8 原生库执行无损流复制（输出 `moov` 前置的 MP4，HEVC 统一写为 `hvc1` 标签以兼容 QuickTime 与系统原生播放器）。各平台加载方式：Windows 先以 `LOAD_WITH_ALTERED_SEARCH_PATH` 加载 `avformat-62.dll` 等使同目录依赖生效；Linux 加载 SONAME `libavformat.so.62`；macOS 加载 `@loader_path` 依赖的 `libavformat.62.dylib`。C 结构体字段偏移在 `FfmpegLayout` 中按 FFmpeg `8.0.1` 头文件硬编码，加载时强制校验 `avutil 60`、`avcodec 62`、`avformat 62` 三个主版本号，不匹配即拒绝执行以防内存越界。**升级 MediaMP 或其 mpv 运行库前必须核对此处**：若主版本变更，须在 WSL 中用 `gcc` 编译 `offsetof` 探测程序按新头文件重算偏移并核对函数签名。输入源通过自定义 `AVIO` 回调（`AvioReader.read` / `seek`，经 `MethodHandles` 绑定并由 ProGuard keep）对接 `RandomAccessMediaSource`（SDK 文件句柄与共享稀疏暂存池），不使用 FFmpeg 内置 HTTP 协议；测试见 `DesktopPikoSegmentDownloaderTest`。
- **显卡设备复位恢复（`GpuDeviceWatch`）**：显卡驱动发生复位（NVIDIA 事件 153 / Windows TDR）后 D3D11 设备即失效，而 Skiko `0.150` 未检查 `HRESULT`，下次调整窗口尺寸时会在 `makeDirectXSurface` 内解引用空指针导致整个 JVM 进程崩溃。`GpuDeviceWatch` 在每次改尺寸前及每秒定时通过反射读取 Skiko 内部 `Direct3DRedrawer.device` 与 `DirectXDevice` 槽位调用 `GetDeviceRemovedReason`，一旦检测到设备失效即驱动 `PikoWindow` 递增 `generation` 重建全部窗口（升级 Skiko 时须对照源码核对内部字段布局；管理员权限执行 `dxcap -forcetdr` 后拖拽窗口即可复现验证）。MediaMP 的底层 mpv 日志经 `MpvLogBridge` 桥接至 `PikoLog`（tag 为 `mpv`）。

### 弹层销毁崩溃规避、模态文件框隔离与窗口外壳

- **测量途中销毁弹层崩溃规避**：Compose Desktop 每帧先拷贝一份「主场景 + 各弹层」列表再依次测量；若测量主层期间某个弹层（菜单、工具提示、对话框）因重组离开组合被立即 `dispose`，轮到测量列表中该弹层时便会抛出 `RootNodeOwner is already disposed` 并终止出帧协程（Compose 上游未修复缺陷）。在测量阶段才触发子组合的容器（`SubcomposeLayout`、`BoxWithConstraints`、`Scaffold` 槽位、懒加载网格）最易触发。多层防御约定：
  1. 包含弹层的自定义布局一律使用普通 `Layout`，禁止使用 `SubcomposeLayout`（如 `CommandBarLayout`、`FloatingPanel` 均因此采用普通 `Layout`；表单下拉不使用自建弹层的 `ExposedDropdownMenuBox`）。
  2. Windows 拖拽窗口边框改尺寸时会同步立即测量，最易撞上响应式形态切换销毁弹层；`WindowFrame` 在拖拽边框期间冻结 `LocalWindowInfo` 尺寸并暴露 `LocalWindowResizing`，按宽度切换侧栏/面板形态的逻辑（如 `PikoMainScaffold` 的 `panelFits`）统一等到松手后再重算。
  3. `PikoWindow` 顶层异常处理器专门识别该异常文案，命中时静默重建出事窗口而不弹崩溃报错框（升级 CMP 时须核对 `require` 异常原文）。
- **AWT 模态文件框专用线程隔离（`AwtDialogs`）**：调用 `FileDialog` 或 `JFileChooser` 必须统一经仅暴露挂起函数的 `AwtDialogs` 在专用后台线程弹出（由 `AwtDialogsGuardTest` 扫描源码 import 强制守护）。在 EDT 界面线程同步弹出 AWT 模态框会就地嵌套一层事件循环并重入渲染一帧，触发 Compose 不可重入的 `FlushCoroutineDispatcher` 将同一协程续体恢复两次而导致整窗崩溃（issue #7，macOS 播放视频同时修改下载目录可稳定复现）。Windows 原生选择器（`FolderPicker`、`SaveFilePicker`）运行在各自独立的 STA 线程上；属主窗口引用须在点击触发当下捕获传入。
- **数据目录（`PikoHome.root`）与单实例锁（`SingleInstance`）**：严禁自行拼接 `user.home`。`:desktopApp:run` 与 `:cli` 使用 `~/.piko-dev`（系统属性 `piko.home`），正式安装版使用 `~/.piko`，Windows 便携包（`Piko.exe` 同级目录存在 `portable` 标记文件；该标记在 `packageReleaseUpdate` 生成清单之后才写入 `.7z` 包，不在 `files.json` 内，防止旧安装版/旧便携版经应用内更新后被误加标记导致数据目录漂移）使用程序目录下的 `data\`（不可写时自动回退至 `~/.piko` 并弹窗告知）。macOS 钥匙串与 Linux Secret Service 条目名对非默认数据目录自动追加命名空间后缀（`PikoHome.secretNamespace`）。`SingleInstance` 通过数据根目录下的 `instance.lock` 文件锁选举主实例，后启动进程将启动参数（`magnet:`、分享链接或转为绝对路径的 `.torrent` 文件）经 Unix Domain Socket（`PikoHome.instanceSocket`）转交主实例并唤醒窗口后立即退出；开发版与正式版因数据根目录不同可并行运行。
- **系统托盘与关窗策略（`WindowsTray.kt`、`Main.kt`）**：
  - **Windows 原生宽字符托盘菜单（`WindowsSystemTray`）**：Compose Desktop 内置 `Tray` 底层依赖 `java.awt.PopupMenu`，在 JDK 18+ 默认 UTF-8 字符集下，Windows AWT 的 `WMenuItemPeer` 仍将 UTF-8 字节直接传给 ANSI 接口 `AppendMenuA`，导致中文 Windows（CP936/GBK）托盘右键菜单必然乱码。Windows 端改为使用 `java.awt.TrayIcon`（仅承载图标与宽字符 Tooltip）配合 FFM 直调 `user32.dll` 宽字符接口（`CreatePopupMenu` + `AppendMenuW` + `TrackPopupMenu`）及 `uxtheme.dll` 深浅色序号（135 / 136），彻底消除编码乱码并获得 Windows 11 原生圆角深浅色菜单。
  - **关窗与静默后台保留**：当存在未完成后台任务（`hasBackgroundWork`）、存在待确认结果或可恢复上下文（`hasDesktopResumeContext`），或用户已开启「最小化到托盘」（`closeToTray`）时，关闭主窗口不退出进程而是隐藏至托盘（若非用户主动开启常驻托盘，则待全部后台任务与待确认上下文清空后自动退出进程）；首次在无任务且未设偏好时点击关闭按钮，弹出带「记住我的选择」的关闭行为询问框。用户已开启「最小化到托盘」或在询问框中选择最小化时静默入托盘，不每次弹系统通知打扰；仅在未开启常驻托盘、因后台仍有任务首次自动转入后台时发送一次系统通知提示。窗口尺寸、位置与最大化状态持久化于 `settings.properties` 的 `window.<名称>.*`。
- **自绘标题栏（`WindowFrame`、`WindowsCaption`）与 Windows 触摸桥（`compose-windows-touch`）**：
  - Windows 不采用 `undecorated` 无边框窗口，而是经 FFM 子类化窗口过程（`WindowsCaption`）：`WM_NCCALCSIZE` 仅裁去顶边系统标题栏，`WM_NCHITTEST` 返回 `HTCAPTION` 与最小化/最大化/关闭三枚按钮的非客户区命中码，从而完整保留 Windows 11 原生贴靠布局（Snap Layouts）、边缘缩放、窗口阴影与 `Win+方向键`；三枚窗口按钮的悬停与按下状态均由非客户区消息驱动而非 Compose 指针事件。
  - AWT 不处理 `WM_POINTER`，会将多点触控与手写笔降级为单点鼠标。`compose-windows-touch` 在 `WindowsCaption` 的外层框架窗口与内部 Skiko 画布窗口过程中拦截客户区 `WM_POINTER*`（不拦截 `WM_NCPOINTER*`，确保标题栏与边框触控仍由系统合成鼠标消息完成拖动与点按钮），在首条指针消息到达时通过反射绑定 Compose 内部 `composePanel`、`_composeContainer`、`mediator` 与 `ComposeScene.sendPointerEvent-` 的 10 参数多指针重载（ProGuard 必须显式保留该未在 Compose 内部直接调用的重载；**升级 CMP 后必须使用 `javap` 对新版 `ui-desktop` jar 核对类名与方法摘要后缀，并打 Release 包实测**）。事件进入 EDT 前合并堆积的 `MOVE` 为 `HistoricalChange` 并显式填充 `originalEventPosition`（防止速度跟踪器从原点起算导致滑动惯性失控）；`ProvideTouchViewConfiguration` 将 Compose Desktop 硬编码的 `18dp` 触摸位移阈值替换为 Android 标准的 `8dp`（鼠标阈值按比例折算后仍不足 1 物理像素，手感不变）。Windows 原生虚拟触摸冒烟测试基于 `InjectTouchInput` 运行于 `:desktopApp:desktopTest`。
- **桌面构建版本号**：`-PpikoDesktopVersion` 仅在 CI tag 发布构建时经 `ORG_GRADLE_PROJECT_pikoDesktopVersion` 传入，并同步写入 `-Dpiko.release-build=true`（应用内更新器仅在携带该标记的正式包中执行启动自动检查）。本地开发构建未传该属性时默认回退为 `1.0.0`（macOS `CFBundleVersion` 首段必须大于 `0`，jpackage 拒绝 `0.x`），因此运行时不得凭版本号区分开发版与正式版。

## macOS（实验性，仅 Apple Silicon `arm64`）

与 Windows 共用同一份 `desktopApp` 源码，DMG 仅在 `release.yml` 的 `macos-15` runner 上原生打包（jpackage 不支持跨平台构建），播放采用 `mediamp-mpv-runtime-macos-arm64` 并走 Metal 渲染，平台集成集中在 `MacOs.kt`（Objective-C 消息发送共用 `MacObjc`）：

- **签名与 AOT 限制**：当前无 Apple 开发者证书，产物为 ad-hoc 签名且未经公证；不生成 AOT 缓存（AOT 训练晚于 jpackage 签名步骤，向 `.app` 内补写缓存会破坏代码签名封印）。
- **系统集成差异**：标题栏通过根面板属性将内容铺入标题栏并调用 Skiko `disableTitleBar` 接管拖动，保留系统原生红绿灯按钮（全屏空间 `WindowPlacement.Fullscreen` 下自动隐藏自绘顶栏）；`magnet:` 链接、`.torrent` 文件、`⌘Q`（窗口可见时走主窗口关闭逻辑，已隐藏在后台时直接退出）与点击 Dock 图标通过 Apple Events 接收（`.torrent` 文件读取与哈希计算移交 IO 线程）；默认协议与文件关联通过 LaunchServices 直接修改（`MacLinkAssociation`，首次普通启动询问一次）；系统通知经 `osascript` 发送，防休眠经 `caffeinate` 维持，外部播放器经 LaunchServices 查询扩展名默认应用后以 `open -a` 传入本机回环代理地址（`MacExternalPlayer`），主修饰键为 `⌘`。
- **整包替换更新**：应用内更新通过 `apply-update-mac.sh` 整包替换 `Piko.app`（先拷贝至同目录旁，通过 `codesign --verify` 校验并清除 `com.apple.quarantine` 隔离属性后再原子替换；任一步骤失败均保留并重新拉起旧包，写入 `failed` 标记供下次启动提示）。

## Linux（实验性，仅 `x64`）

因 MediaMP `0.5.0` 仅提供 `linux-x64` 的 mpv 运行库，Linux 端仅构建 `x64` 产物：

- **固定应用 ID `dev.nihildigit.Piko`**：`.desktop` 文件、AppStream 元数据（`package/linux/`）、图标名与 X11 `WM_CLASS` 统一固定为 `dev.nihildigit.Piko`（满足 Flathub 域名小写、末段可大写的包名规范，按 `nihildigit.dev` 验证；Android 与 macOS 已发版的 `dev.piko`、`dev.piko.desktop` 保持不变）。AWT 默认将主类名 `dev-piko-desktop-MainKt` 设为 `WM_CLASS`，会导致桌面环境 Dock 无法匹配图标；启动建窗前由 `LinuxDesktop.setWmClass` 反射修改 `XToolkit`（仅 Linux 宿主注入 `--add-opens java.desktop/sun.awt.X11`）。注意：`package/linux/dev.nihildigit.Piko.desktop` **刻意省略** FreeDesktop 1.5 新增的 `SingleMainWindow` 键，以兼容 Ubuntu 22.04 旧版 `desktop-file-validate` 校验（AppImageHub 审核环境要求）。
- **打包产物与 AOT 缓存**：`./gradlew :desktopApp:packageReleaseAppImage`（CI 在 `xvfb-run` 下运行以支持开窗 AOT 训练；本地若遇 Gradle 9.6 下 foojay 0.9 下载失败，可在 `org.gradle.java.installations.paths` 中手动指向本地 Zulu 25）先产出 jpackage `app-image`，再由 `package/linux/build-appimage.sh` 使用固定版本与 SHA-256 摘要的 `appimagetool` 及运行时产出三份附件：原始 `.tar.gz`（供后续 Flathub 打包）、内嵌 `gh-releases-zsync|NihilDigit|piko|latest|piko-linux-x64-*.AppImage.zsync` 更新信息的 `.AppImage`、以及写相对 URL（兼容镜像拉取）的 `.AppImage.zsync`。AppImage 每次挂载于随机 `/tmp/.mount_*` 路径，但 JDK AOT 仅校验类路径各项的相对位置，因此 AOT 缓存正常生效；squashfs 时间戳精确到秒，沿用偶数秒对齐处理，**严禁设置 `SOURCE_DATE_EPOCH`**（`mksquashfs` 检测到该环境变量会将所有文件时间戳改写为同一值，导致 AOT 缓存整份失效）。
- **原生库与硬件 OpenGL 要求**：mpv 运行库 jar 内不含符号链接，同一动态库存在真实文件名、SONAME 与无版本名三份副本，`bundledAppResources` 仅提取 SONAME 副本置于 `mpv/` 目录（各库自带 `$ORIGIN` RUNPATH，无需污染 `java.library.path` 或执行 `patchelf`）；运行库依赖 `glibc 2.38+`（Ubuntu 24.04 / Debian 13 及以上）。MediaMP 在 Linux 上经 GLX 与 Skiko 共享纹理，仅支持 `LinuxOpenGLRedrawer`；无硬件显卡驱动（虚拟机、xvfb、默认未设 `GALLIUM_DRIVER=d3d12` 的 WSLg）回退至 `llvmpipe` 软件渲染时视频画面恒黑且打开不返回，播放器窗口据此给出明确硬件加速提示。安装包内置硬件播放自检入口：`-Dpiko.selftest=play` 配合环境变量 `PIKO_SELFTEST_PATH`（`SelfTest.kt`、`PlaybackSelfTest.kt`）。
- **平台胶水与默认关联（`LinuxDesktop.kt`、`LinuxLinkAssociation`）**：**严禁调用 `java.awt.Desktop`**（其在 Linux 上会加载系统 GTK 与系统 `glib`，与 `mpv/` 内自带的库发生 SONAME 冲突）。打开 URL 与文件统一调用 `xdg-open`；系统通知与「在文件管理器中显示」经 `gdbus` 调用 `org.freedesktop.Notifications` 与 `org.freedesktop.FileManager1.ShowItems`（失败回退为打开父目录）；防休眠经 `systemd-inhibit`；使用系统原生标题栏，`Ctrl` 为主修饰键；GNOME 默认无系统托盘，关窗后台传输时提示再次启动 Piko 唤回窗口。以 AppImage 运行时首次启动询问协议关联，向 `~/.local/share/applications` 写入指向 `$APPIMAGE` 的 `NoDisplay=true` `.desktop` 并执行 `xdg-mime default`（`Exec` 路径仅在包含保留特殊字符时加引号，避免无桌面环境如 CI xvfb 下 `xdg-open` 直接解析引号失败；每次启动若检测到 AppImage 移动位置则自动刷新 `Exec`；WSL 环境下 `xdg-open` 会转发至宿主 Windows，本机调试需改用 `gio open`）。
- **zsync 差分更新与重启脱壳**：仅在 AppImage 环境（`$APPIMAGE` 非空）启用应用内更新，Flatpak 环境（`FLATPAK_ID` 或 `/.flatpak-info`）直接禁用（`updater = null`）。检测到新版后先拉取并按 GitHub 摘要校验 `.zsync`，由纯 Kotlin 实现的 `Zsync.kt`（兼容 zsync 0.6.2，含 MD4 滚动校验）比对本机旧 AppImage 并通过 HTTP Range 仅下载缺失块（不捆绑只信任 SHA-1 且无法走 `ghfast.top` 镜像的 `appimageupdatetool`），拼装后核对整包 SHA-256，校验失败则自动回退整包下载。新文件写入同目录旁 `.<文件名>.piko-update`，校验通过后无需等待进程退出即可直接 `rename` 覆盖（运行中的旧实例由 FUSE 保持旧 inode）；重启新实例时由 `setsid sh` 等待当前 PID 退出后再 `exec` 新 AppImage（防止撞上单实例锁），且**子进程环境必须剔除 `_JPACKAGE_LAUNCHER` 环境变量**（jpackage 启动器在本进程注入了该变量，子进程若继承它会导致新启动器跳过读取 `Piko.cfg` 而直接打印 `java` 帮助退出；任何由应用拉起自身的新进程均须遵守此条）。Linux 更新冒烟脚本位于 `package-smoke/linux.sh`（终止测试进程时仅终止挂载点内的 `usr/bin/Piko` JVM 进程，严禁先杀外层 AppImage FUSE 运行时以免拆掉挂载点引发 `SIGBUS`）。
